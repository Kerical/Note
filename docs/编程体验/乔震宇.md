## 我完成的具体工作

这次团队编程中，我负责个人记账本的统计模块，主要文件是 `statistics_service.py`。核心功能包括计算总收入、总支出、结余和账单笔数，以及按类别、月份汇总收支，并通过 `GET /api/stats` 接口向前端提供数据。

最初的代码主要完成统计计算，之后根据团队接口约定，将核心函数调整为 `summarize_records()`，补充了 `count` 字段，并增加 `get_statistics()`，连接存储模块和查询模块。这样的拆分让我更清楚地理解了各个函数的职责：读取数据、筛选记录、汇总计算和返回响应分别由不同部分完成。

## 遇到的问题与解决方法

我印象最深的是列表展示与统计范围的区别。列表默认只显示最近10条记录，而统计需要计算全部符合条件的账单。如果直接使用列表返回的数据计算，就可能遗漏记录，导致金额和笔数不准确。

因此，统计模块复用了3号成员提供的 `filter_records()`，先筛选全部账单，再进行汇总，同时通过 `allow_limit=False` 拒绝统计接口中的条数限制参数。验证时也加入超过10条记录的场景，检查统计是否完整。

金额处理也需要统一规则。项目接口和存储使用整数“分”，例如1250表示12.50元，统计时直接进行整数累加，避免浮点数误差。此外，还需要考虑空数据、跨月份和同类别多笔账单等情况，不能只验证一组正常数据。

## 团队协作体验

统计模块需要与其他成员的代码配合：从1号的存储模块读取账单，使用3号的查询模块筛选，再将汇总结果交给前端展示。2号的新增和删除功能接入后，也需要验证账单变化是否能正确反映在统计结果中。

开发初期，部分依赖模块尚未提交，因此先使用替身模块验证调用和接口行为，等真实模块完成后再进行联调。这个过程让我认识到，单个函数计算正确，并不代表整个系统已经能够正常运行，还需要检查参数、返回字段和错误处理是否一致。

通过分支和 Pull Request 提交代码，我也更加理解了团队开发的流程。完成自己的文件以后，还需要关注主仓库更新，确认代码已合并，并检查与其他模块的配合情况。
